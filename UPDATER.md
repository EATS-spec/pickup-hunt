# Cloud updater contract

This repository is a deployment template. Cloning it creates no cloud schedule, database, credentials, or connection to the public demo. Configure and verify an updater for your own deployment. It must run without a developer's Mac or any browser tab and should refresh data rather than republish source.

For a Sites-hosted installation, the optional owner MCP connection uses `pickup_hunt_tick` once, then `pickup_hunt_health`. Enable `TRUST_SITES_IDENTITY=true` and set `OWNER_EMAIL` only behind the trusted Sites proxy that strips visitor-supplied `oai-authenticated-user-*` headers and injects authenticated identity. Keep that flag false on local or generic/self-hosted Workers: raw HTTP identity headers are not proof of authentication. The tick performs at most one due shared query through the atomic request gate; an idle or waiting result is normal.

For a generic HTTP installation or a dedicated timer, generate a random credential and store only its SHA-256 verifier as `CALLBACK_TOKEN_HASH` (or `UPDATER_TOKEN_HASH`). Send the original only to your HTTPS deployment as `Authorization: Bearer ...`. POST an empty JSON object to `/api/refresh`, then read `/api/updater-health`. Never put the original credential in source, URLs, logs, prompts, or Git history.

For a protected deployment, the hosting service's access check and the app's callback authorization are separate. A hosting credential does not replace the dedicated token whose hash is configured in `CALLBACK_TOKEN_HASH` or `UPDATER_TOKEN_HASH`. Configure hosting access through your provider and keep the callback credential scoped to your own deployment.

If the callback is rejected, verify the deployed token hash and the timer's configured origin and credential. The owner MCP connection is an alternative only behind the trusted Sites proxy described above. If neither path is authorized, repair the configuration; do not expose the updater, weaken its guard, or republish source on every scheduled check.

A successful tick must persist `lastTickAt`; a successful inventory query also persists `lastSuccessfulCheckAt` and the job result. Read those values back. HTTP429/541 from Apple triggers persisted backoff; respect it and do not issue another raw pickup request. Never bypass the queue using direct Apple calls.

Stay quiet on ordinary idle/waiting/successful runs. Notify the owner only for a persistent scheduler/authentication failure, a broken catalog/feed schema, or required owner action. The updater drains the private opt-in Web Push queue even on idle/waiting ticks. Only current watched stock and visitor-requested tests may be sent. It must not send purchase offers or order devices.

The optional Google Apps Script relay under `apps-script/` supports five-minute callbacks to `/api/refresh`. Its runbook explains how to set your own `PICKUP_HUNT_SITE_ORIGIN`, store the dedicated token in Script Properties, authorize the script, and install its trigger. Only the credential's SHA-256 verifier belongs in the Site environment. The timer authenticates and verifies a fresh persisted heartbeat before replacing its own trigger. It records `PICKUP_HUNT_LAST_SCHEDULED_SUCCESS_AT` separately from a manual setup run, so inspect timer status or execution history to verify unattended operation. A Sites installation can retain an hourly native schedule as a fallback. Do not assume a new checkout has either timer merely because source exists.

Set `SCHEDULE_CADENCE_MINUTES` to match the scheduler actually enabled, then deploy the saved version to apply environment changes. Five-minute ticks do not guarantee five-minute checks for every search: the shared fair queue processes at most one distinct search per tick and preserves the global gate/backoff. Manual searches execute the same gated cloud path. No schedule is a real-time SLA. New active watches become eligible automatically; expired/stopped watches cease polling.
